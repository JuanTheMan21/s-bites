# Filling one block

You are given one block: its type, its role in the scene, the segment's narration, and the
**measured** duration of the narrated audio the whole scene is on screen for. You return the
content payload for that block type.

**You do not write markup.** No HTML, no CSS, no class names, no timing attributes, no inline
styles. Templates own all of that. A value containing a tag is a bug that reaches the rendered
frame, because the template will either escape it — the viewer sees `<b>` — or trust it. Every
field is plain text.

## Density is set by duration

The measured duration is how long the whole scene is on screen, not just this block. It is not
advice; it is the budget, shared with whatever other block sits alongside this one.

**How many items** is not yours to choose. Each field states its own range, and those ranges come
from what the block can lay out at a readable size. Stay inside the range you are given, and use
the low end of it when the scene is short.

**How much text is in each item** is what duration governs:

- **Under 12 seconds** — the fewest words that carry the point. Two or three words per item,
  labels rather than sentences. The viewer glances once.
- **12 to 30 seconds** — a short phrase each, up to about six words.
- **Over 30 seconds** — still a short phrase each. **A longer scene does not earn more words**;
  it earns more room to breathe. Nothing on screen is read twice.

When the narration covers more than the block can hold, cut the least important item down to the
field's minimum rather than shortening every item into fragments. Five items nobody can parse is
worse than three they can.

## Writing for a screen

- **Fragments, not sentences.** "Compiles once, runs many times." Not "The query is compiled a
  single time and can then be run many times." Text is read in a glance.
- **No terminal punctuation** on a fragment. A short phrase ending in a full stop reads as a
  truncated sentence.
- **Parallel grammar** across items in a list or a column. All noun phrases, or all verb phrases —
  a mix reads as a mistake even when the content is right.
- **Front-load the distinguishing word.** In a two-panel scene, the panels are scanned side by
  side, so the word that differs should be near the start.
- **Length limits are about the longest item, not the average.** One item at twice the length of
  its neighbours breaks the layout for all of them.

## `anchor_phrase` — narration-anchored timing, everywhere an item has one

Any field named `anchor_phrase` (a step's, a node's, an item's, a line's, a key term's) exists so
the visual reveal can land on the exact word that describes it, instead of an arbitrary evenly
spaced beat. The rule is the same everywhere it appears:

- Copy it **VERBATIM** from this segment's own narration — the exact words, in the exact order
  they appear. A paraphrase, a summary, or words from your own `text`/`label`/`caption` field
  instead of the narration cannot be found in the audio and the reveal falls back to a generic
  beat, which is worse than no anchor at all.
- Keep it short — 3 to 8 words is enough to be unique without risking a typo against the real
  narration text.
- Every item that has this field needs its own value. Never leave it as a copy of the item's own
  display text (a node's `label`, a code line's `text`) — narration rarely repeats a short label
  verbatim, and matching against it either finds nothing or finds the wrong, out-of-order moment.

## Per block type

- **`title`** — the headline is the video's subject, not a sentence about it. The subtitle earns
  its place only if it adds a second dimension; omit it rather than restating the headline in more
  words.

  `key_terms` (0 to 4) are short standalone terms or short phrases pulled from this segment's own
  narration — the kind of thing a viewer would want called out while the card is still on screen,
  not padding to fill time. Each one needs its own `anchor_phrase`. Leave `key_terms` empty rather
  than inventing terms the narration doesn't actually emphasize — an empty list is a normal,
  expected answer for a short or purely introductory title segment.
- **`text_panel`** — items must be parallel and mutually exclusive. When this block is one side of
  a two-panel comparison, the headline is that side's short label ("Unsafe", "Safe"), and item *n*
  must address the same dimension as the other panel's item *n* — that row-wise correspondence is
  what makes the pair readable, not two unrelated lists. Each item has its own `text` (the point
  itself) and `anchor_phrase` (see above).
- **`code_panel`** — the code must be real and runnable-looking, short enough to read on screen,
  and the highlighted lines must be the ones the narration is actually about. Prefer eight clear
  lines to twenty realistic ones; elide with a comment rather than truncating mid-statement.
  Highlight one region, not four.
- **`stat_callout`** — the value is the whole scene, so it must be a number a viewer can hold:
  round it, and put the precision in the context line if precision matters. The context says why
  the number is surprising, not where it came from.

  **`value_number`, `prefix`, `suffix`:** set `value_number` to the plain numeric value `value`
  renders as — 200000 for "200,000", 94 for "94%" — and the animated tier counts up to it live
  instead of only scaling in. Fill it whenever `value` *is* a clean number: an integer or a value
  with at most one decimal place, with no qualifier baked into the digits themselves. Leave it
  `null` when `value` is a ratio ("1 in 5"), a range, an approximation the narration itself hedged
  ("about half", "roughly 3 billion"), or anything a count-up would make look more precise than it
  is — counting up to a number implies that number is exact, and a viewer reads a count-up as a
  fact being *proven*, not estimated. Put a symbol that reads as part of the number itself in
  `suffix` ("%", "x", "ms") and a unit set apart from it in `unit` — not both for the same thing.
  `prefix` is for a leading symbol like "$". Never derive `value_number` by parsing `value`'s
  text; decide it independently from the same fact `value` was built from.

- **`graph_diagram`** — set `layout` to `chain` for a strictly linear process (a pipeline, an
  attack chain, a request path) — each node a step, `edges` exactly the consecutive pairs in
  order, `positions` empty. Set it to `graph` for real topology (a network, a tree, a hub, DP
  state transitions, a linked list, a cycle) — `edges` any connections, `positions` empty unless a
  specific layout genuinely matters (leave it empty by default; the template lays nodes out on
  its own using a real rank-based layout). `traversal` highlights nodes one at a time in narration
  order — leave it empty for a diagram that just sits there once revealed. Each node's `id` is
  never shown to the viewer; only `label`/`caption` are. A caption is for a step whose name is not
  self-explanatory; captioning every node makes the diagram a list again. Each node's own
  `anchor_phrase` (see above) marks when it should first appear — do not reuse the node's `label`
  for this, a short label is exactly the case that fails to match reliably.

  Each edge's `label` is a short weight, cost, or condition shown on the connection itself — a
  distance for Dijkstra, a big-O cost for a DP transition, a guard condition for a state machine.
  Fill it only when the topic genuinely has such a fact; leave it `null` for a plain connection.
  Never invent a number or condition the narration does not supply.
- **`array_grid`** — `cells` are the array or list itself, left to right (or top to bottom, if
  `orientation` is `vertical` — reach for that when the content reads more naturally as a stack).
  `steps` is what makes the block genuinely animated, and `op` says what kind of change each step
  is:
  - `narrow` — the active range shrinks without translating (a binary search's midpoint check).
    `remaining_start`/`remaining_end` must sit *inside* the previous step's range.
  - `shift` — the range translates by its own fixed width (a sliding window advancing).
    `remaining_end - remaining_start` must equal the previous step's width.
  - `push` — the range's end grows by exactly one cell (a stack push, a queue enqueue).
    `remaining_end` must be exactly one more than the previous step's; `remaining_start` unchanged.
  - `pop` — the range's end shrinks by exactly one cell (a stack pop, a queue dequeue).
    `remaining_end` must be exactly one less; `remaining_start` unchanged.

  `end_operation` is a separate, optional `+`/`-` badge at the step's acting cell — set it to
  `plus` for a cell entering (`push`, or `shift`'s leading edge), `minus` for a cell leaving
  (`pop`, or `shift`'s trailing edge), `none` for a plain `narrow` that already reads clearly from
  its own strike-through. Each step's `anchor_phrase` must be copied **verbatim** from the
  narration at the moment that change happens — an anchor that paraphrases the narration cannot be
  found and the step falls back to an arbitrary beat. Leave `steps` empty for a static array with
  nothing eliminated, shifted, pushed, or popped; do not invent a change the narration never
  describes.
- **`code_diff`** — `lines` interleave `context`/`add`/`remove` exactly as a real diff would,
  top to bottom. `text` never carries a leading `+`/`-`/space — the template supplies that from
  `op`. Use this for a before/after change (a fix, a vulnerability being patched, a refactor), not
  for showing code that never changes — that is `code_panel`. Each line's `anchor_phrase` marks
  when it should reveal — since a line's own `text` is source code, not narration, it can never be
  used as its own anchor; describe the moment the narration is discussing that line in the
  narration's own words instead.
- **`sequence_diagram`** — `actors` are the participants, in the order their lanes should read
  left to right; two to five of them. `messages` are the exchange, in narration order, each with
  its own `anchor_phrase` — six to eight messages at most, since more will not fit above the
  caption band. Use this for a protocol, handshake, or request-response exchange — a shape that is
  fundamentally about *who talks to whom, in what order*, not a `graph_diagram`'s topology.
- **`timeline`** — `events` are three to seven labelled moments, left to right in chronological
  order — the order given is the order drawn, never re-sorted by `date_label`. `date_label` is a
  short marker (a year, a date, "Day 3") shown but never parsed, so it can be as loose as the
  narration itself is.
- **`icon_panel`** — three to six icon + label chips for a labelled set of discrete concepts,
  components, or steps that are more icon-shaped than list-shaped ("the three layers of the OSI
  model," "what a firewall blocks," "the pieces of a JWT"). Each item's `icon` must be the
  closest real match from the closed vocabulary you were given — never force a stretch; if
  nothing genuinely fits the concept, this segment is not an `icon_panel` segment, use
  `text_panel` instead. `label` is the concept itself, two or three words, and each item's own
  `anchor_phrase` (see above) marks when it should appear.

## Consistency with the narration

The scene must not contradict the narration, and must not introduce a fact the narration never
mentions. If the narration says "roughly ten times", the stat says "10x" — not "9.7x" because it
seemed more credible. **Never invent a number, a code detail, a graph edge, an edge label, or a
step for a slot.** If the block needs a fact the narration does not supply, use the qualitative
phrasing the narration used.
