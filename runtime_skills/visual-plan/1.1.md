# Planning a video's visuals

You are given every segment in one video at once: each one's title, summary, narration, measured
duration, and the visual intent chosen for it at outline time. You return one scene plan per
segment -- a layout, the blocks that fill it, and (sparingly) any annotations -- for the whole
video in one answer.

**You do not write markup and you do not write content yet.** This step decides *shape*: which
blocks, in what arrangement. A later step fills each block's actual words, numbers, and code. A
block whose content you can already picture is a sign you are choosing well; do not try to
describe that content here.

## Why this step exists

Every earlier version of this pipeline planned each segment's visual alone, with no idea what any
other segment looked like. The result was six-plus segments in a row using the same shape,
because nothing was ever positioned to notice. You are the first thing in this pipeline that sees
the whole video, and that is the entire point of this step: **enforce variety as a fact about the
video, not a hope about each segment.**

## Hard rules

- **No block type may be the primary block of more than a third of the video's segments.** In a
  video with thirty segments, no single block type should be the *first* block of more than ten
  of them -- the fraction is what matters, not any particular segment count.
- **Consecutive segments must not share the same primary block type**, except when
  `continues_previous` is genuinely true for a segment picking up exactly where the last one left
  off (see below) -- that is the one case sameness is the point.
- **Segment 0 is always a title card and you do not need to plan it.** Whatever you return for
  segment 0 is ignored. Spend your attention on the rest.

## Choosing a layout

- `SINGLE` -- one block fills the frame. The default, and right for most segments.
- `SPLIT_HORIZONTAL` -- exactly two blocks side by side. Reach for this when a segment is
  genuinely two things set against each other (two approaches, code next to what it produces,
  before and after) -- not as a way to fit more content into one segment.

## Choosing blocks

| Block | Earns its place when | Do not use it for |
|---|---|---|
| `title` | The opening, or a genuine change of subject mid-video | Any segment with real content |
| `text_panel` | Parallel points, or one side of a `SPLIT_HORIZONTAL` comparison | A sequence where order matters -- that is `graph_diagram` |
| `stat_callout` | One number that changes how the viewer sees the topic | A number mentioned in passing |
| `code_panel` | The idea *is* the code, and specific lines are the point | A before/after change -- that is `code_diff` |
| `code_diff` | A fix, a vulnerability being patched, a refactor -- code that changes | Code that never changes -- that is `code_panel` |
| `graph_diagram` | An ordered process (`layout: chain`) or real topology -- a network, tree, hub, DP transitions, a linked list (`layout: graph`) | A collection with no inherent order -- that is `array_grid` or `text_panel` |
| `array_grid` | A collection being searched, sorted, narrowed, or built -- a binary search, a sliding window, a stack or queue | A static list with no change over time -- that is `text_panel` |
| `sequence_diagram` | Who talks to whom, in what order -- a protocol, handshake, request-response exchange | Topology with no inherent time-ordering -- that is `graph_diagram` |
| `timeline` | A run of historical or evolutionary events in chronological order | A process with only one path through it -- that is `graph_diagram`'s `chain` mode |

`array_grid` is easy to under-use out of habit. If the narration describes eliminating,
narrowing, discarding, halving, pushing, popping, or shifting a window over a set of items in
order -- a binary search, a sliding window, a stack, a queue -- that is exactly what it is for,
even if the segment's outline-time visual intent suggests something else. The outline-time intent
is a hint from before the real narration existed; trust the narration over it.

## Continuity

Set `continues_previous: true` when this segment's visual should read as picking up exactly where
the previous segment's left off -- the same diagram with one more node added, the same array still
narrowing -- rather than a fresh, unrelated composition. This is what separates a real explainer
from a slideshow: most segments should be `false`, but a genuine sequence (successive steps of one
process, successive narrowings of one search) should say so.

## Anchoring blocks to the narration

Set `anchor_phrase` to a short phrase copied **verbatim** from the segment's own narration,
marking the moment that block should appear. Use the segment's actual words, not a paraphrase --
an anchor that does not appear in the narration text cannot be found and the block falls back to
appearing at the scene's start. Leave it `null` when a block should simply be present throughout.

## Annotations

An annotation is a small overlay mark on one of THIS scene's own blocks -- a cursor pointing at
something, a check confirming something is correct, a warning flagging a mistake. It is **not** a
block: it does not fill its own space in the layout, it sits on top of content another block
already provides.

Use annotations **sparingly** -- at most one or two per scene, only where the narration is
genuinely pointing something out (a specific mistake, a completed step, something worth noticing).
Most scenes should have none at all. An annotation on every scene reads as decoration, not
emphasis, and stops meaning anything.

`target_block_index` must name a block in THIS segment's own `blocks` list (0-based). For a
`SPLIT_HORIZONTAL` scene, it must stay within whichever panel the annotation is about -- never a
block in the other panel. `target_item_index` points at one numbered sub-element of that block
(a specific array cell, code line, or graph node) when the annotation is about one specific thing
rather than the block as a whole -- leave it `null` to attach to the whole block.

## What you are not deciding

Do not write any block's actual content -- headlines, item text, code, array cell values,
annotation targets' content. A later call does that, one block at a time, once your plan is
fixed. Do not invent facts the narration does not support; your job here is shape and timing, not
substance.
